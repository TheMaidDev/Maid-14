# Зачистка спурьезных ошибок локализации (Unknown messageId) — масштабный свип

## Контекст

Последние фиксы (#220, #240, #248, #249, #254) чинили спам в консоли `Unknown messageId (culture): key`, хотя текст отображался нормально. Механизм: `RobustToolbox/Robust.Shared/Localization/LocalizationManager.cs:64-118` при неудачном поиске ключа логирует Warning и **возвращает входную строку как есть**. Два класса бага:

- **Паттерн A — двойная локализация**: код передаёт уже локализованную строку в `Loc.GetString(...)` повторно (пример: RCD-меню `Loc.GetString(entProto.Name)`, где `EntityPrototype.Name` уже локализован; `BoundKeyHelpers.ShortKeyName`). Фикс — убрать внешний `Loc.GetString`, маркер `// MAID BEGIN/END fix double localization` со старым кодом в `/* */`.
- **Паттерн B — сырые строки вместо ключей**: у прототипа `name:` содержит человеческий текст, а код правомерно зовёт `Loc.GetString(proto.Name)` (пример из #248: `name: Blueshield Officer` у джоб). Фикс — добавить ключи в `Resources/Locale/{en-US,ru-RU}/_Maid/...` и направить прототип на ключ (YAML правится с `# MAID fix localization` — прецедент #248/#254).

Заметок предыдущих агентов в `.claude/docs/` об этом нет — «информация от предыдущих агентов» = сами фиксовые коммиты и маркеры `// MAID fix double localization`.

Предварительный аудит ~40 сайтов `Loc.GetString(x.Name)` в клиенте показал: большинство корректны по конвенции (gas `gas-*`, эмоции `chat-emote-name-*`, вывески `barsign-prototype-name-*`, тайлы `tiles-*`, департаменты, виды, джобы/антаги после фиксов, категории стора `store-category-*`). Реальные риски: (1) ключи есть в прототипе, но отсутствуют в en-US или ru-RU ftl (пример: 194 TTS-голоса в `_Maid/Voice/tts_voices.yml` против ftl в обеих культурах — нужна сверка каждого), (2) сырые строки в менее ходовых прототипах (cargo-accounts, bounty, guide entries, lathe-категории, white-контент).

## Шаги

### 1. Аудит-скрипт (одноразовый, вне репозитория)
Скрипт (Python `-I`, положить рядом, не в репо), который:
- Собирает все Fluent message-ID из `Resources/Locale/en-US/**/*.ftl` и `Resources/Locale/ru-RU/**/*.ftl` (regex на `^id =` и `id.attr =`).
- Для каждого прототипного типа из списка сайтов ниже парсит `name:` из соответствующих YAML и проверяет: (а) существует ли ключ в обеих культурах, (б) выглядит ли значение как сырая строка (пробелы/заглавные).
- Выводит таблицу: файл прототипа → значение → чего не хватает (en/ru/обе/сырая строка).

### 2. Паттерн B — данные прототипов
По результатам аудита: для каждого прототипа с сырой строкой или отсутствующим ключом — добавить ключи в `Resources/Locale/en-US/_Maid/` и `Resources/Locale/ru-RU/_Maid/` (зеркалить структуру существующих `job/jobs.ftl`, `antag.ftl`, `tts/tts-voices.ftl`), в YAML заменить значение на ключ с комментарием `# MAID fix localization`. Прототипы в `_Maid/` правятся свободно, `_Goobstation`-YAML — только с маркерами. Код-проекты `Content.Goobstation.*` не трогаем.

### 3. Паттерн A — двойная локализация
Греп-свип по подозрительным сигнатурам: `Loc.GetString(` от `.LocalizedName`, `Identity.Name`, `EntityName`, `GetRoleName`, `entProto.Name`, `proto.Name` где proto — EntityPrototype, `TryGetString` + `GetString` на одном ключе. Каждый подтверждённый случай — убрать внешний вызов с MAID-маркерами по образцу `Content.Client/RCD/RCDMenu.xaml.cs:80` (`// already localized`).

### 4. Верификация
- `dotnet build` решения (компиляция контента).
- Повторный запуск аудита: ноль сырых строк, ноль отсутствующих ключей в обеих культурах.
- Ручная проверка (опционально, с пользователем): запуск клиента, открыть лобби-антаглист, эмот-меню, лат/стор/гайдбук/ID-консоль — консоль чиста от `Unknown messageId`.
